# dashboard

## Purpose

Vendor console root: the Overview (a daily briefing: regulars and cadence, self-explaining base stats, a visits trend, "worth a look" actions, what the rewards cost this month, recent activity, and your programs) and the account nav/layout, plus the server actions (`actions.ts`) that back stamping, engine "visit" events, redemption, card regeneration, and QR-token resolution for the whole dashboard tree.

## Contents

- `actions.ts` — server actions (`stampAction`, `adjustStampAction`, `recordVisitAction`, `redeemPlantAction`, `regenerateCardAction`, `resolveTokenAction`, `lookupAction`, `redeemAction`, `redeemVoucherAction`, `applyPointsOffsetAction`, `saveQkitEarnConfigAction`, `saveCustomerNotifySettingsAction`) that stamp/play/redeem/regenerate cards and save qkit-earn/customer-notify config, each RLS-scoped via `requireVendor`; `redeemVoucherAction` redeems one catalog-mode Points Club reward voucher via the `redeem_voucher_by_token` RPC, mapping its raised `already_redeemed`/`expired` errors to friendly copy (generic fallback otherwise) — the mutation behind `redeem-voucher/`'s scan-confirm screen, distinct from `redeemAction`'s Stamp/Plant oldest-active-voucher path; `adjustStampAction` (used by `customers/[phone]/adjust-stamp-form.tsx`) is the manual day-2 ops correction tool — a `±` delta with a required reason, via `loopkit.adjust_stamp` (migration `0042`), free-tier; `redeemAction` also reads the vendor's `vendor_notify_settings` row via `customerNotifyEnabled` before calling `notifyCustomerByPhone` — a missing row resolves to enabled (backward compat), only an explicit `customer_telegram_notify_enabled: false` row skips the call. `saveCustomerNotifySettingsAction` upserts that same row on `vendor_id` (same shape as `saveQkitEarnConfigAction`), not Pro-gated. `stampAction`'s `rewardReady` now goes through `getProgress` (the real engine dispatch) instead of a flat `stamp_count >= stamps_required` check — needed once Points Club's 2 new modes make that comparison meaningless (`adjustStampAction`'s own `rewardReady` call is untouched — it's a classic-Stamp-only tool per its own comment). `applyPointsOffsetAction` is the offset-mode redemption tool: deducts a vendor-entered points amount from a scanned card via `apply_points_offset` and returns the dollar figure for the vendor to apply manually at their own register. `resolveTokenAction` now returns a `kind: "card" | "voucher"` discriminated result — a card-token miss falls back to `voucher_by_token` before erroring, since the same QR surface also carries Points Club voucher tokens minted at catalog redemption

## Connectivity

`layout.tsx` wraps every route below (including all 9 subfolders) with vendor-auth enforcement and the `DashboardNav` header; its inline sign-out action posts through the nav's dropdown form. `page.tsx` is the dashboard home (the vendor Overview): it fetches `getVendorStats` / `countExpiredVouchers` / `listActivity` / `getVendorOverviewInputs` (`@/lib/stats`) / `getVendorProfile` in parallel, feeds them through `dashboard-view.ts`'s `buildOverviewModel` / `buildOverviewPrograms` / `pickServeDefault`, and renders `overview/*` plus `serve-cta.tsx`. `actions.ts` is the shared server-action surface: `serve-customer.tsx` (used by `counter/`) calls `stampAction`/`recordVisitAction`/`lookupAction`/`redeemPlantAction`/`regenerateCardAction`/`adjustStampAction` (the last for the served-strip Undo), `redeem-button.tsx` calls `redeemAction`, `redeem-voucher/`'s `RedeemVoucherConfirm` calls `redeemVoucherAction`, and `scan-button.tsx` calls `resolveTokenAction`; `qkit-earn-settings.tsx` (used by `settings/`) calls `saveQkitEarnConfigAction`. `redeemAction` is also the confirmed live redemption trigger point for reward-redemption vendor alerts (not `redeemOldestVoucher` in `src/lib/vouchers.ts`, which has no caller anywhere in `src/app/`) — after a successful `redeem` RPC call it calls `notifyVendor` (`@/lib/merqo-customer-notify`), which posts to merqo's own shared Telegram bot (Phase A2; loopkit no longer runs its own bot/webhook), wrapped so a failure never changes `redeemAction`'s own returned result. As a sibling call, `redeemAction` also calls `notifyCustomerByPhone` (`@/lib/merqo-customer-notify`) with the card's phone, reusing any standing merqo-owned Telegram connection the customer already made via qkit — a customer who never connected via qkit (or connected without a phone) is a silent no-op, and the call is wrapped so a failure there never changes `redeemAction`'s own returned result either. That call is itself gated by the vendor's own `vendor_notify_settings` row (read via `customerNotifyEnabled`, an authenticated RLS-scoped lookup) — a vendor who finds the confirmation off-brand can turn it off from `settings/`'s `CustomerNotifySettings` panel, which calls `saveCustomerNotifySettingsAction`; a vendor who's never touched the setting (no row at all) still gets it, since the app-code default is "on," not the column default alone. `card.ts`'s `StampCard` type is shared by `actions.ts`, `redeem-button.tsx`, and `serve-customer.tsx`. `program-switcher.tsx` is a cross-cutting control reused by the `activity/`, `customers/`, `stats/`, and `counter/` subfolders to switch which program the view acts on. `dashboard-view.ts` is `page.tsx`'s pure view-model (`buildOverviewModel` and friends), unit-tested without rendering the async component. `layout.tsx` also renders `DashboardTour` (from `src/components/`), which auto-runs once on `page.tsx`'s `[data-tour="shop-qr"]` anchor (now the Overview's head row) for a vendor whose `vendors.tour_seen_at` is still null, stamping it as soon as the tour starts (not when it finishes) via a `keepalive` POST to `src/app/api/tour-seen/`. `layout.tsx` itself also stamps `tour_seen_at` durably, server-side, via `@/lib/tour-prefs`'s `stampTourSeen`, the moment it sees a null value on its own read — closing the race where a fast page refresh could beat the client-fired POST and cause the tour to re-fire. `referrals/` owns its own `actions.ts` (not this folder's shared one) since `createReferralHostAction` only ever writes a `referral_hosts` row, not a card/stamp event; the actual referral-crediting logic it powers lives in `loopkit.vendor_join_referred`/`apply_referral_credit` (migration `0040`) and `src/features/card-check/api/actions.ts`'s `checkStatusAction`, triggered from the public `/c?ref=` link `referrals/` generates, not from anything in this folder.
