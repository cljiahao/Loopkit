# setup

## Purpose

Vendor onboarding and program-management flow at `/setup` — create, edit, migrate (change type), prep a replacement, activate, or schedule retirement for loyalty programs, with a live animated preview of the customer card.

## Contents

- `actions.ts` — server actions `saveProgramAction` (create/edit, enforces the free/Pro program-count gate; on a stamp-program edit it also writes `programs.reward_cost_cents` from the form's optional `reward_cost_dollars` field via `@/lib/money`'s `dollarsToCents`, blank meaning null, and only on the edit path since `create_program` has no such parameter), `changeTypeAction` (owner-scoped `replace_program` transaction retires, creates and links a successor; failed creation rolls back retirement), `prepProgramAction` (free-tier: create a hidden second program), `activateProgramAction` (flips a prepped program to active), and `scheduleRetirementAction` (Pro-only: schedules a future cutover date to a successor program). All four of `saveProgramAction`/`changeTypeAction`/`prepProgramAction` now also read `stamp_style`/`stamp_color` from the submitted `FormData` (previously silently dropped, so nothing a vendor picked in the Stamp style section ever saved) and run the shared `mechanicGateError` helper — `resolveFamilyAndStyle` (from `card-type-picker.ts`) plus `@/lib/program`'s `canUseFamily`/`canUseStampStyle`/`canUseColor` — before any write, returning the same upsell-style error as the count gate when a free vendor's mechanic/style/color choice needs Pro.
- `card-type-picker.test.ts` — unit tests for `card-type-picker.ts`: the 4-family/per-family-style-count shape, `isSingleStyleFamily` (true only for Stamp Card and Points Club), `resolveFamilyAndStyle`'s type/variant → family/style mapping for every existing combination, and a round-trip check that every style's `styleToTypeAndVariant()` resolves back to itself via `resolveFamilyAndStyle`.
- `card-type-picker.ts` — pure family/style data and mapping for the type picker; groups the backend's 5 program types (2 of which already fan out into variants) into 4 vendor-facing families (Stamp Card, Growth, Points Club, Chance Card) each with their own style tiles, via `FAMILIES`, `familyOf()`, `isSingleStyleFamily()`, `resolveFamilyAndStyle()` (saved type/variant → family/style, for the picker's active-tile highlight), and `styleToTypeAndVariant()` (style → the type/variant pair actually saved) — no new DB type/variant value is introduced, "chance" is a UI-only grouping label.
- `edit-impact-dialog.tsx` — submit-button wrapper: a plain submit when there is nothing to warn about, otherwise a button that first opens an `AlertDialog` listing what current cardholders will see, and only submits the form on confirm.
- `page.tsx` — `SetupPage` server component; requires a vendor, applies due scheduled cutovers, seeds/reads the shared `merqo.vendor_profile` row (degrading to null on failure), resolves `resolveSetupView`'s single active view from the request's query params, and renders exactly that one view: the "Your programs" management list (`?manage=1`, with a "+ New program" link back to the plain create view), `SetupForm` (create/edit/migrate/prep), `ScheduleRetirementForm` (scheduling), or a Pro-upsell `ProLock`. A "Manage your programs" link surfaces on the plain create/upsell view whenever any programs exist. The at-cap upsell view's page header now reads "Add a program" / "You've reached your plan's program limit." instead of repeating the exact same heading+paragraph the `ProLock` card below it already showed. For the edit view it computes `editingCardCount` via `@/lib/cards`'s server-only `programCardCount` and passes it as the `SetupForm` `cardCount` prop (the prep-view `SetupForm` is left at the default 0). Both `SetupForm` renders also get `allowedFamilies`/`allowedStampStyles`/`allowedCustomColor` from a single `getEntitlement(pro)` computed once at the top of the page.
- `preview-animation.dom.test.tsx` — jsdom test covering `usePreviewAnimation`'s ticking, celebrate-then-reset, head-start-seeded reset, immediate restart on recipe change, real win/loss rolls for lucky/wheel/scratch, and the reduced-motion static fallback.
- `preview-animation.ts` — `usePreviewAnimation()` hook; drives the real `applyVisit()`/`getProgress()` engine on a 2s timer to simulate a customer visiting, so the setup preview animates through the actual engine transitions (respects `prefers-reduced-motion`); for wheel/scratch ticks, holds the rolled result back for a `REVEAL_MS` (1400ms) `revealing` sub-phase (masking `landedId` to `null`) so the preview can play a spin/scratch anticipation animation before the win/lose signal commits — presentation-only, the real customer card has no equivalent delay since the roll already happened server-side at scan time; also sets `lastChanceResult` on every lucky tick (previously only wheel/scratch did), since Lucky Tap now shares the same win/lose pill. Now also destructures `scratchCoverStyle` from its input and folds it into `recipeKey`, so changing the cover-style picker in Rules restarts the ticking loop immediately like any other recipe field edit. Same treatment for the newer `stampStyle`/`stampColor`, and now also `pointsRedemptionMode`/`pointsCatalog`/`pointsOffsetRate`.
- `preview-card.tsx` — `PreviewCard` client component; a static-height snapshot of the customer card view (mirrors `ProgramCardStatus`'s view-kind switch) with an optional celebration burst and a transient win/lose popup for chance types; accepts a new `revealing` prop forwarded from `usePreviewAnimation`, passed to `Wheel` as `spinning` and to `ScratchCard` as `scratching` during the reveal-delay window; renders `LuckyBox` for a `kind: "lucky"` view, and the win/lose pill now also fires for Lucky Tap (not just Wheel/Scratch); its outer container is now `@/components/card-shell.tsx`'s `CardShell` (pointer-tilt), replacing a plain `<div>`. The corner win/lose pill only fires for scratch/lucky now — `Wheel` renders its own win/lose overlay directly on itself (see `wheel.tsx`), so it's excluded from the pill's condition. Still tracks a `wheelSettled` flag (reset to `false` the moment `revealing` starts a new wheel spin, flipped back to `true` via `Wheel`'s `onSettled` callback) purely to gate the celebration burst for wheel views — `CardBurst` is a shared component that lives at this level for every card type, so `Wheel` can't gate it itself; without this the burst could fully finish playing well before the wheel visually stopped spinning. Now also accepts an optional `vendorAvatarUrl` prop (defaults `null`); for a plain-dot stamp view it resolves the vendor's chosen stamp mark via `@/lib/stamp-mark`'s `resolveStampMark(view, vendorAvatarUrl)` and passes the result to `StampDots`' `mark` prop, so the live preview shows the same preset-icon/photo mark a real customer card would render. The scratch branch's `ScratchCard` call now also passes `coverStyle={view.coverStyle}` (the chance `ProgressView`'s new scratch-only field, `src/lib/engine/chance.ts`'s `ScratchCoverStyle` — `"foil" | "wax" | "ticket"`, ignored for wheel), so the live preview always shows the vendor's actually-picked cover material. The stamp/dots branch's `StampDots` call now also passes `style={view.style}`/`color={view.color}` (the dots `ProgressView`'s newer plain-dots-only fields, `src/lib/engine/stamp.ts`'s `StampVisualStyle` — free for every vendor, no Pro gate), so the preview always shows the vendor's actually-picked stamp skin.
- `preview-card.dom.test.tsx` — jsdom tests asserting `PreviewCard` renders each view kind, name/reward fallback placeholders, win/lose popups for non-wheel chance types (scratch/lucky — Wheel's own overlay is covered directly in `wheel.dom.test.tsx`), that the corner popup does NOT fire for a wheel result, the card-burst celebration overlay, and (via `Wheel`'s `data-testid="wheel-rotor"`) that a rotation transform is present for wheel views. The cup-variant plant view check asserts via `Cup`'s `data-cup-coffee` hook, not an implementation detail of its old stroked-outline shape. Its plant/cup view fixtures include the `filled`/`total` counter fields `ProgressView`'s plant kind now carries.
- `preview-state.ts` — exports `buildPreviewProgram()`, `buildInitialCard()` (mirrors `enroll_card`'s head-start seed math), and `buildPreviewProgress()`; assembles a synthetic program/card from the form's current field values and runs them through the real `getProgress()`. `PreviewInput` now carries an optional `scratchCoverStyle?: ScratchCoverStyle` (scratch-only, ignored by every other program type — same optional-field pattern as `pointsPerVisit?`), passed as `buildChanceConfig()`'s new 5th argument in `buildPreviewProgram`'s wheel/scratch branch. Same pattern for the newer `stampStyle?: StampVisualStyle`/`stampColor?: string` (plain-dots-only), passed straight into the stamp branch's `config.stamp_style`/`stamp_color`. Also carries optional `pointsRedemptionMode?`/`pointsCatalog?`/`pointsOffsetRate?` (points-only), threaded into the stamp branch's `config.redemption_mode`/`catalog`/`offset_rate`.
- `schedule-retirement-form.dom.test.tsx` — jsdom test asserting `ScheduleRetirementForm` renders a successor picker (defaulting to the first successor) and date input, and submits the program id, chosen successor, and date.
- `schedule-retirement-form.tsx` — `ScheduleRetirementForm` client component; a successor `<Select>` plus a date input, submitted via `useActionState(scheduleRetirementAction)`.
- `setup-form.dom.test.tsx` — jsdom test covering the live preview updating on keystroke/head-start toggle, submitted field values, the two-step family/style type picker (Step 1's 4 family tiles, a multi-style family expanding to its styles plus a "← Back" link, Back returning to Step 1, single-style families (Stamp Card, Points Club) completing immediately with no Step 2, and Lucky Tap now part of Chance Card's multi-style style sub-step), type-switch resetting name/reward, per-variant (Flame/Points/Cup/Sprout) type/variant/label submission behavior, Spin the Wheel's segment editor plus its odds-weight `InfoTooltip`, the Scratch Card style showing its "Scratch cover" picker and submitting the chosen `scratch_cover_style` (picking a `ToggleGroup` option by its `role: "radio"` — Radix's `type="single"` `ToggleGroupItem` exposes `radio`, not `button`), Points Club's "Points redemption" section defaulting to catalog mode with `stamps_required`/its "Points required" label hidden and submitting the 2-item default catalog as JSON, and picking "Points = cash" submitting `offset_rate_points`/`offset_rate_dollars` instead, and a dedicated "create-flow step wizard" block asserting the 3-step Type→Basics→Rules indicator, `Next: Rules` staying disabled until a card name is entered, Back preserving already-entered field values, the stamp-mark section staying collapsed behind "Show advanced options" until asked for, and that edit mode never shows any of this wizard chrome; plus a "reward cost field" block asserting the field renders for a stamp card in edit mode, prefills in dollars from `reward_cost_cents`, and submits `reward_cost_dollars`; plus a "reward expiry default" block asserting the field pre-fills `90` for a new stamp program and stays blank when editing a program with none set; plus a "Pro gating" block asserting a free vendor sees a lock badge on the Growth family tile and on the premium `ToggleGroupItem` stamp styles (Wax seal etc, queried by `role: "radio"`) plus a "Custom colors need Pro." note, none of which show for a Pro vendor passed the full `allowedFamilies`/`allowedStampStyles`/`allowedCustomColor` props.
- `setup-form.tsx` composes create/edit/replace/prep actions, family/style selection, mounted wizard steps and the live preview. State and mechanic fields live in the local modules described below. Native input names, entitlement enforcement and edit-impact confirmation remain unchanged.
- `setup-page.dom.test.tsx` — jsdom test calling `SetupPage` directly (mocking `listPrograms`/`isPro`/`SetupForm`/`ScheduleRetirementForm`/`getVendorProfile`) covering all 8 `SetupView` outcomes: create (Pro, with a Manage link), upsell (free-tier at cap, still with a Manage link), first-run create, the manage list (with a + New program link), edit, prep, schedule (the Pro-vendor regression case), and migrate — asserting each view is the only one rendered.

## Server-component note

The back nav here renders `@merqo/ui`'s `BackButton` with no
`LinkComponent` override. This page is a Server Component, and passing
`next/link` in as a prop sends a function across the Server → Client
boundary (`BackButton` is a client entry point), which Next rejects
at render. `BackButton` falls back to a plain `<a>`.

## Component ownership

`SetupForm` composes the native form and mounted wizard panels. `use-setup-form-state.ts` owns defaults, action selection, live preview state and edit impact. `setup-basics-fields.tsx`, `setup-points-fields.tsx` and `setup-rules-fields.tsx` own mechanic field groups while preserving submitted names. Preview and customer cards share `components/progress-visual.tsx`; preview timing remains local.
