# components

## Purpose

Shared React components: the reward-mechanic visualizations (flame, plant,
cup, wheel, scratch, dots, points bar), general-purpose UI (back button,
image uploader, pro-lock, reward celebration), app-wide providers, and the
`landing/` and `ui/` subtrees.

- `wheel.tsx` — `Wheel`: SVG spinning-wheel visualization computing per-segment pie slices and a rotation angle that lands on `landedId`; each segment optionally takes a vendor-picked `color` (hex, via the new `color-picker.tsx`) — white outlined text (`paint-order`+`stroke`, not a real CSS text-shadow which SVG `<text>` lacks) keeps the label legible against any custom color; falls back to emerald (reward) / muted rose (non-reward) when unset, replacing a low-contrast gold/muted-gray pairing that didn't read clearly as win-vs-lose at a glance. Rotation is driven entirely by `requestAnimationFrame`-computed real constant-angular-deceleration ("friction") kinematics — not a CSS transition/animation at all, since a fixed CSS easing curve can't be told "you're moving at exactly this velocity right now, decelerate smoothly from there," which is what produced the "spinning at a constant speed, then suddenly so fast" artifact a two-phase CSS-curve handoff had. The free-spin phase (target segment still unknown, masked by the parent) itself continuously decelerates from the first frame; the moment the target becomes known, a second physics solve reads the _exact_ velocity the free-spin phase had reached and computes a fresh deceleration that brings the wheel to a dead stop precisely on the target angle — continuing the same velocity across the boundary rather than restarting a new curve. Skips the whole simulation and jumps straight to the resolved angle under `prefers-reduced-motion`. **Owns its own win/lose result** — computed directly from the landed segment's `reward` flag the instant it settles, rendered as an overlay directly on the wheel itself (not a separate caller-positioned badge) — replacing an earlier design where the caller tracked a separately-threaded result value that had to stay in sync with this component's own async settle animation, a real synchronization bug surface. Takes an optional `onSettled({won})` callback, fired with that same true result exactly when the settle simulation finishes, purely so callers can gate something else (e.g. `PreviewCard`'s celebration burst, which lives at that level for every card type) on "has the wheel visually finished" — not for the result itself.

## Connectivity

`landing/` composes the marketing sections rendered by `src/app/page.tsx`;
`ui/` is the shadcn/ui primitive layer (`Button`, `AlertDialog`, etc.) that
both this folder's own components (`back-button.tsx`, `reward-celebration.tsx`)
and `landing/` build on. The reward-mechanic visualizations
(`flame-layers.tsx`, `plant.tsx`, `cup.tsx`, `wheel.tsx`, `scratch-card.tsx`,
`stamp-dots.tsx`, `points-bar.tsx`, `lucky-box.tsx`) each render one
`src/lib/engine/` strategy's `ProgressView` variant and are selected by the
dashboard/customer card views based on the program's `type`/`variant`;
`card-shell.tsx` is the shared outer wrapper both card views (`PreviewCard`/
`ProgramCardStatus`) render one of these inside, giving all of them the same
sheen/tilt treatment regardless of which visual they host.
